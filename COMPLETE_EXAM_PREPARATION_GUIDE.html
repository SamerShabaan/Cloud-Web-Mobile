1. Formula Sheet, Key Metrics & Bit Arithmetic

System Availability (A)
A = MTTF / (MTTF + MTTR) = E[Uptime] / (E[Uptime] + E[Downtime])
• MTTF (Mean Time To Failure): Average operational time before a crash.
• MTTR (Mean Time To Repair/Recovery): Average time needed to restore the system.
• MTBF (Mean Time Between Failures): MTBF = MTTF + MTTR.
Component Topologies: Serial vs. Parallel
Serial (SPOF): A_total = A_1 × A_2 × ... × A_n
Parallel (Redundant): A_total = 1 - (1 - A_1)(1 - A_2)...(1 - A_n)
• Serial chain: A single failure brings down the entire chain. Total availability is strictly lower than the least reliable component.
• Parallel replicas: System survives as long as at least one replica runs. Total availability is higher than any single component.
Gifford Quorum Consistency (Majority Consensus)
Read-Write Overlap: R + W > N
Write-Write Exclusion: W > N / 2
Where N = total replicas, R = read quorum size, W = write quorum size.
• R + W > N: Guarantees that any read quorum intersects with the most recent write quorum by at least one replica holding the newest version number.
• W > N/2: Prevents split-brain by ensuring two concurrent writes cannot both acquire a write quorum.
Protocol Buffers: Field Key & ZigZag Bit Arithmetic
Field Key = (Field Number << 3) | Wire Type
ZigZag Encode: f(n) = (n << 1) ^ (n >> 31) [32-bit arithmetic shift]
ZigZag Decode: n = (z >> 1) ^ -(z & 1)
• Varint (Wire Type 0): Groups of 7 data bits per byte in Little-Endian. MSB (Bit 7) = 1 if more bytes follow; MSB = 0 on the final byte.
• ZigZag: Maps negative integers to small positive integers so they don't consume 10 bytes in standard Varint encoding: 0 ↦ 0, -1 ↦ 1, 1 ↦ 2, -2 ↦ 3, 2 ↦ 4, -3 ↦ 5.

2. Lecture 01: History & Evolution of Computing

The course opens by analyzing the cyclical pendulum of computer science architectures between centralized and decentralized paradigms:

Era / Architecture Characteristics & Mechanics Main Drawback / Failure Mode
Mainframe Monolithic central computer, time-sharing OS, dumb terminals (VT100). Zero processing or storage at user desks. Extreme hardware costs, single point of failure, no custom local UI.
Personal Computer (PC) Decentralized commodity x86 hardware, local computing power and disk storage. Full user autonomy. Isolated data silos, no effortless multi-user synchronization, difficult backup/software management.
Client / Server 2-Tier: Fat client connects directly to SQL DB (heavy coupling).
3-Tier: Web Client → Application Server (Business Logic) → Database Server.		 2-tier suffered from massive upgrade costs and leaked database credentials. 3-tier required custom infrastructure scaling.
Peer-to-Peer (P2P) Symmetric nodes (servents = server + client). Decentralized routing. Napster (central index), Gnutella (flooding), BitTorrent (tracker + torrent chunks + tit-for-tat incentives). Overcame asymmetric consumer broadband (slow DSL uplinks), but lacked central governance and guaranteed latency.
Grid Computing Federation of geographically distributed, heterogeneous, idle computing clusters (e.g. Globus Toolkit, SETI@home). Batch-oriented scientific workloads, complex authentication/authorization, poor support for interactive web apps.
Cloud Computing Centralized data centers offering virtualized resource pools accessible globally via standardized web APIs. Vendor lock-in, latency over public internet, dependency on provider uptime and security boundaries.
Exam Concept: John Locke's Three Acts of the Mind
Prof. Weis uses the 17th-century philosopher John Locke's epistemology to explain how complex distributed architectures are constructed from simple primitives:
  1. Combination: Joining several simple ideas into one compound entity. Example: Combining thousands of cheap commodity PCs and hard drives into unified racks and cloud clusters.
  2. Relation: Setting two ideas side-by-side to examine interactions without merging them into one. Example: Network protocols, client-server relationships, primary-secondary replica topologies.
  3. Abstraction: Separating general qualities from real, physical existence. Example: Hardware virtualization abstracting physical silicon into virtual CPUs and RAM; PaaS abstracting away the operating system and runtime.
NIST Definition of Cloud Computing
You must know the 5 Essential Characteristics:
  1. On-Demand Self-Service: Automated provisioning without human operator intervention.
  2. Broad Network Access: Services accessible over standard networks via heterogeneous devices.
  3. Resource Pooling: Provider resources pooled to serve multi-tenant consumers dynamically.
  4. Rapid Elasticity: Capabilities dynamically scaled up and down based on demand.
  5. Measured Service: Metered resource usage (pay-per-use) transparently billed.
Plus the 3 Service Models (IaaS, PaaS, SaaS) and 4 Deployment Models (Public, Private, Hybrid, Community).

3. Lecture 02: Datacenters & IaaS

Datacenter Engineering & Metrics

  • PUE (Power Usage Effectiveness): Ratio of total facility electricity consumption to the electricity delivered directly to IT computing equipment. Older centers: ~1.8–2.0. Modern hyperscale facilities: 1.1–1.2.
  • Cooling Architectures: Hot Aisle / Cold Aisle Containment prevents cold intake air from mixing with hot exhaust air. Free Cooling / Economizers use outside cold air or river water to bypass power-hungry mechanical chillers.
  • Power Redundancy Chain: Utility Grid → Backup Diesel Generators → UPS Battery Banks (bridges the ~15–30s generator spin-up gap) → Power Distribution Units (PDUs) → Dual Power Supplies (A/B Feeds) per server chassis.

IaaS: Amazon Web Services (AWS) EC2

Pricing Model Commitment & Flexibility Cost Profile Ideal Use Case
On-Demand No commitment, pay by the second/hour. Full flexibility to start/stop anytime. Highest hourly cost. Unpredictable traffic spikes, short-term testing, early-stage apps.
Reserved Instances 1 to 3-year contract for designated instance types. Significant discount (up to 70%). Predictable, steady baseline production workloads (e.g. core database servers).
Spot Instances Bidding on unused datacenter capacity. AWS can terminate instances with a 2-minute warning when demand rises. Steepest discount (up to 90%). Stateless, fault-tolerant batch workloads, video rendering, MapReduce worker nodes.
Cloud Networking Essentials
• Elastic IP: A static, public IPv4 address that can be programmatically re-routed from a failed instance to a healthy standby instance.
• VPC & Subnet Isolation: Public subnets connect directly to an Internet Gateway for reverse proxies/load balancers. Private subnets have no public inbound routes and use a NAT Gateway for outbound traffic (used for databases).
• Security Groups vs. Network ACLs: Security Groups are stateful and apply at the virtual network card (instance) level. Network ACLs are stateless and apply at the subnet boundary.

4. Lecture 03: Virtualization & Sandboxing

Hypervisor Types

  • Type 1 (Bare-Metal): Runs directly on physical silicon (e.g. VMware ESXi, Xen Dom0, Linux KVM). Maximum performance, lowest overhead, carrier-grade.
  • Type 2 (Hosted): Runs as an application inside a host operating system (e.g. VirtualBox, VMware Workstation). Higher overhead due to host OS abstraction.

Popek-Goldberg Virtualization Theorem & The IA-32 Flaw

The IA-32 Virtualization Hole (Frequent Exam Question)
Popek-Goldberg Theorem (1974): An architecture is classically virtualizable using pure Trap-and-Emulate if and only if all sensitive instructions are a strict subset of privileged instructions:
Sensitive Instructions ⊆ Privileged Instructions
• Privileged Instruction: Traps into the OS kernel if executed in unprivileged user mode.
• Sensitive Instruction: Alters hardware configuration or behaves differently depending on CPU execution mode.

The x86 Hole: 32-bit x86 (IA-32) violates this theorem! It contains 17 sensitive instructions that are unprivileged (e.g. POPF, PUSHF, SMSW, LAR, LSL).
Consequence: When a deprivileged guest OS in Ring 1 or 3 attempts to change interrupt flags via POPF, the CPU does not trap. It simply ignores the modification or leaks host register contents silently. The guest OS fails!

The Three Solutions to the x86 Virtualization Gap:

  1. Binary Translation (VMware): Dynamic binary inspection at runtime. Sensitive unprivileged opcodes are discovered and dynamically rewritten in-memory into safe hypervisor function calls. Works with unmodified guest OSes, but incurs translation overhead.
  2. Paravirtualization (Xen): The guest OS source code is modified. Unsafe instructions are replaced with explicit Hypercalls (analogous to system calls). High performance, but requires modifying the guest OS kernel (cannot run proprietary, closed-source OSes without source modifications).
  3. Hardware-Assisted Virtualization (Intel VT-x / AMD-V): Introduces two new hardware operating modes:
    • VMX Root Operation: Hypervisor execution mode.
    • VMX Non-Root Operation: Guest OS execution mode.
    • Both modes feature the complete Ring 0–3 privilege hierarchy! The guest OS runs in Non-Root Ring 0. Sensitive operations trigger a hardware-controlled VM-Exit back to Root mode. Transitions are managed via the hardware VMCS (Virtual Machine Control Structure) using VMLAUNCH and VMRESUME.

Memory Virtualization: Shadow Page Tables vs. EPT

  • Shadow Page Tables (Software): VMM maintains a shadow page table mapping Guest Virtual Address (GVA) directly to Host Physical Address (HPA). Guest page tables are marked write-protected; every guest page table update causes a page fault trap and a costly VM-Exit.
  • Extended Page Tables (EPT / Hardware): Hardware MMU performs a two-dimensional page walk (GVA → GPA via Guest CR3, then GPA → HPA via Hypervisor EPTP). Updates do not cause VM-Exits, but TLB misses take longer (up to 16 memory reads for a 4-level walk).

Containerization & Linux Sandboxing

  • Linux Namespaces (Isolation of View): pid (process tree), net (IPs/ports/routes), mnt (filesystem root), ipc (POSIX semaphores/queues), uts (hostname), user (UID mapping), time (clock offsets).
  • Control Groups (cgroups v2 - Resource Governance): Enforces resource quotas (cpu.max, memory.max, process count pids.max, I/O limits).

5. Lecture 04: PaaS & Google App Engine (GAE)

GAE Architectural Rules

  • Stateless Compute: Instances write no permanent files to disk. Any local filesystem write is ephemeral.
  • Sandbox Constraints: No background threads surviving past the HTTP request lifespan. Hard request execution deadline (e.g. 60 seconds). Scaling down to zero instances.
  • Cloning & Pooling: Rapid process cloning for handling sudden traffic surges.

Datastore, Entity Groups & Transactions

The Entity Group Write Limit (Crucial Exam Concept)
• Entities belong to an Entity Group defined by their root ancestor path: Parent / Child / Grandchild.
• ACID Transactions: Guaranteed only within a single Entity Group.
• Throughput Limit: An Entity Group can handle approximately 1 write per second! Optimistic concurrency control aborts conflicting concurrent writes with a ConcurrentModificationException.
• Cross-Group (XG) Transactions: Support transactions across up to 5 distinct Entity Groups using two-phase commit.

Design Pattern: The Sharded Counter

To overcome the 1 write/sec limit for global counters (e.g. view counts, upvotes):

Write Flow: Client Request ──> Pick Random Shard (i ∈ 1..N) ──> Write to Shard_i (1 write/sec per shard) Read Flow: Read Total ──────> Query Shard_1 ... Shard_N ───────> Sum = Shard_1 + Shard_2 + ... + Shard_N

Total write capacity scales linearly to $N \times 1\text{ write/sec}$. Reads are slightly more expensive (querying $N$ entities), but writes never bottleneck.

Memcache & CAS (Compare-and-Swap)

In-memory volatile cache. To prevent lost updates during concurrent read-modify-write cycles:

  1. Client fetches value and token: value, cas_id = memcache.get(key, for_cas=True)
  2. Client modifies value locally.
  3. Client writes atomically: memcache.cas(key, new_value, cas_id)
  4. If another client updated the key first, cas_id is stale and the write safely fails.

6. Lecture 05: SaaS, Multi-Tenancy & DaaS

Multi-Tenancy Database Architectures

Pattern Isolation Cost / Density Risk & Tradeoff
Separate Database Maximum Very expensive High infrastructure cost, backup overhead for $N$ DB instances.
Shared DB, Separate Schemas Medium Moderate DDL schema migrations become complex across thousands of tenant schemas.
Shared DB, Shared Schema Lowest Maximum density, lowest cost Data isolation is purely logical via tenant_id column. A bug omitting WHERE tenant_id = ? leaks tenant data!

Desktop as a Service (DaaS) & Cloud Gaming

  • VNC / RFB: Pixel/framebuffer based. Transmits dirty pixel rectangles. Platform-agnostic, but heavy on bandwidth; lags on video and dynamic UIs.
  • X11: Primitive/command based. Sends vector and drawing instructions. Efficient for basic UIs, but suffers severe latency penalties over WAN due to synchronous round-trips.
  • Cloud Gaming: Round-trip latency budget must remain strictly below 80–100 ms (ideally < 50 ms). Involves input capture, uplink, simulation, GPU render, hardware video encode (NVENC), downlink, client decode, and display refresh. Uses UDP/WebRTC.

7. Lecture 06: Distributed Algorithms, CAP & Paxos

The CAP Theorem (Brewer, Gilbert & Lynch)

In an asynchronous network prone to partitions ($P$), a distributed data store can guarantee at most two out of three guarantees:

  • Consistency (Linearizability): Every read receives the latest write or an error.
  • Availability: Every non-failing node returns a non-error response.
  • Partition Tolerance: The system operates despite arbitrary network packet drops or delays.

Since network splits cannot be avoided in physical reality, systems must choose between CP (preserve consistency by rejecting requests in partitioned nodes) or AP (preserve availability by returning stale/divergent data).

The Paxos Consensus Algorithm (Leslie Lamport)

PROPOSER ACCEPTORS (Majority Quorum Q) │ │ │──────── Phase 1a: Prepare(n) ────────────────>│ │<─────── Phase 1b: Promise(n, max_n, max_v) ───│ │ │ │──────── Phase 2a: Accept(n, v) ──────────────>│ │<─────── Phase 2b: Accepted(n, v) ─────────────│

Step-by-Step Execution:

  1. Phase 1a (Prepare): Proposer selects a unique, monotonically increasing proposal number $n$ and sends Prepare(n) to a majority of Acceptors.
  2. Phase 1b (Promise): If $n > \text{all previously seen proposal numbers}$, the Acceptor promises never to accept proposals numbered less than $n$, and returns Promise(n, max_accepted_n, max_accepted_val).
  3. Phase 2a (Accept): Once the Proposer receives promises from a majority:
    • If any Acceptor reported an accepted value, the Proposer must adopt the value associated with the highest max_accepted_n.
    • If all returned values are null, the Proposer can propose its own value $v$.
    • Proposer sends Accept(n, v) to the majority.
  4. Phase 2b (Accepted): If the Acceptor has not promised to ignore proposal $n$, it registers $(n, v)$ and notifies the Proposer and Learners with Accepted(n, v).
Multi-Paxos Optimization
In standard Paxos, each decision takes 2 Round Trips (Phase 1 + Phase 2). In Multi-Paxos, a stable leader is elected once via Phase 1 with a lease. For subsequent log entries, Phase 1 is skipped entirely, committing values in just 1 RTT (Phase 2 only)!

8. Lecture 07: Security & OAuth 2.0 PKCE

Password Security & Rainbow Tables

  • Rainbow Tables: Time-memory tradeoff precomputing chains alternating between a hash function $H(p)$ and reduction functions $R(h)$: $P_0 \xrightarrow{H} H_0 \xrightarrow{R_1} P_1 \dots \xrightarrow{R_k} P_k$. Only start and end values are saved in memory.
  • Salt: Random cryptographic string per user appended before hashing. Stored in plaintext. Invalidates precomputed tables by forcing an attacker to generate a unique table per user.
  • Slow Hashing: bcrypt, scrypt, Argon2, PBKDF2 with tunable computational and memory cost.

OAuth 2.0 Authorization Code Flow with PKCE

CLIENT (App) USER BROWSER AUTH SERVER RESOURCE SERVER │ │ │ │ 1. │ Generate Verifier & Challenge │ │ │ (Challenge = SHA256(Verifier)) │ │ 2. │── Send Auth Request + Challenge ────────>│ │ │ │ 3. User Login │ │ │ │<── 4. Auth Code ──│ │ 5. │<── Receive Auth Code ────────────────────│ │ │ │ │ 6. │── Token Request (Code + Verifier) ──────>│ │ │ (Auth Server validates SHA256(Verifier) == Challenge) │ 7. │<── Access Token (+ Refresh Token) ───────│ │ │ │ 8. │── API Request with Bearer Token ────────────────────────────────>│ 9. │<── Protected Data ───────────────────────────────────────────────│

Why PKCE is mandatory for SPAs and Mobile Apps: Public clients cannot protect a static client_secret from reverse engineering. Without PKCE, malicious apps could hijack the redirect URI and steal the Authorization Code. PKCE ensures that only the client instance that generated the random code_verifier can exchange the authorization code for an access token.

10. Lecture 09: Google File System (GFS)

Architecture & Design Assumptions

  • Runs on cheap commodity PCs → component failure is normal.
  • Files are huge (hundreds of MBs to multi-GBs).
  • Workload: large streaming reads (read-once) and sequential appends (write-once). No random file writes.
  • 64 MB Chunks: Replicated 3-fold across separate racks.
  • Decoupled Control & Data: Master handles metadata in RAM; Clients stream data directly to/from Chunkservers.
  • No Data Caching: Neither Client nor Chunkserver caches file data (only OS buffer cache). Avoids cache invalidation complexity.

Write Flow: Daisy-Chain Pipelining

Client ──(1. Get chunk locations)──> Master Client <──(Replica list: Primary + Secondaries)── Master Client ──(2. Stream Data)──> Secondary A ──(Data)──> Primary ──(Data)──> Secondary B Client ──(3. Write Command)──> Primary Primary ──(4. Serialized Write with offset)──> Secondaries Client <──(5. Ack)── Primary
Record Append "At-Least-Once" Semantics
• Client specifies no offset. GFS appends at an offset chosen by the primary.
• If data exceeds 64 MB chunk boundary, primary fills chunk with padding, tells secondaries to pad, and replies: "Retry on next chunk".
• If append fails at any replica, client retries. Chunks may contain padding, gaps, and duplicate records.
• Exam Rule: GFS guarantees At-Least-Once append semantics. Client applications must filter duplicates using unique record IDs and checksums!

11. Lecture 10: Google BigTable & NoSQL

The BigTable Data Model

BigTable Sorted Map Mapping
(row:string, column_family:qualifier:string, timestamp:int64) ──> string
  • Rows: Up to 64 KB, lexicographically ordered. Reads/writes under a single row are strictly atomic. Partitioned into 100–200 MB Tablets.
  • Column Families: Small number (dozens), unit of access control and type grouping. Unbounded dynamic column qualifiers.
  • Timestamps: 64-bit integer versioning. Automatic garbage collection of older versions.

3-Level Tablet Location Hierarchy

[Chubby Lock Service] ──> Stores location of Root Tablet │ ▼ [Root Tablet] ───────> Stores locations of all METADATA Tablets (never splits) │ ▼ [METADATA Tablets] ────> Stores locations of all User Tablets │ ▼ [User Tablets] ───────> Contain actual user data key-value ranges

Storage Engine & Compactions

  • Commit Log (GFS): Write-ahead log for durability.
  • Memtable (RAM): Sorted memory buffer for active writes.
  • SSTables (GFS): Immutable sorted files with 64 KB data blocks and index blocks at the file end.
Compaction Type Action Purpose
Minor Compaction Flushes a full Memtable into a new SSTable on GFS. Reclaims RAM and truncates commit log.
Merging Compaction Merges several SSTables and Memtable into fewer SSTables. Reduces read lookup overhead.
Major Compaction Rewrites all SSTables of a tablet into exactly one SSTable. Physically eliminates deleted keys (tombstones) and obsolete versions.

12. Lecture 11: Web Frontends, NaCl & WebAssembly

DOM & HTML5 APIs

  • DOM Node Types: Document, Fragment, Element, Text, CDATA, Attribute (Note: Attribute nodes are NOT child nodes in the DOM tree!).
  • Web Storage: localStorage (persists indefinitely across tabs/sessions) vs. sessionStorage (cleared when browser tab closes).
  • IndexedDB: Asynchronous, transactional, indexed NoSQL object store in browser (W3C standard replacing WebSQL).
  • Web Workers: Multi-threading via asynchronous message passing (postMessage / onmessage). No shared memory, no locks, no deadlocks.

Google Native Client (NaCl) & Software-based Fault Isolation (SFI)

The Variable-Length Instruction Attack & 64-Byte Alignment
• The Threat: x86 opcodes are variable length (1 to 15 bytes). An attacker can compile legal instructions, but jump into the middle of an instruction byte sequence. The CPU decodes the byte fragment as a completely new, unauthorized instruction (e.g. sysenter or segment register override)!
• The Solution:
  1. Mandatory 64-byte instruction alignment for all indirect branch targets.
  2. Gaps before the 64-byte boundary are padded with NOPs so a valid instruction always begins at each 64-byte boundary.
  3. Indirect jumps must clear the lower 6 bits via bitmasking: 
    and $0xffffffc0, %eax   ; Clear lowest 6 bits (force multiple of 64)
jmp *%eax

14. Worked Exam Problems & Solutions

Problem 1: Consensus Tracing
Paxos Scenario with Dueling Proposers

A cluster consists of 5 Acceptors ($A_1, A_2, A_3, A_4, A_5$).

  • $P_1$ sends Prepare(10) to $A_1, A_2, A_3$. All reply with Promise(10, null, null).
  • Before $P_1$ starts Phase 2, $P_2$ sends Prepare(20) to $A_3, A_4, A_5$. All reply with Promise(20, null, null).
  • Now $P_1$ sends Accept(10, "Val_A") to $A_1, A_2, A_3$.

Question a: How do $A_1, A_2$, and $A_3$ respond to $P_1$'s accept request?
Question b: $P_2$ sends Accept(20, "Val_B") to $A_3, A_4, A_5$. Is `"Val_B"` committed?

Step-by-Step Solution:

a) $A_1$ and $A_2$ have only promised proposal 10. Since $10 \ge 10$, they accept and reply Accepted(10, "Val_A").
$A_3$, however, promised $P_2$ to ignore proposals < 20 ($20 > 10$). Hence $A_3$ rejects $P_1$'s accept message.
$P_1$ only collects 2 acceptances. In a 5-node cluster, a majority quorum requires $\lfloor 5/2 \rfloor + 1 = 3$. Proposal 10 is NOT committed.

b) $P_2$ received promises from $A_3, A_4, A_5$ with no previously accepted values. $P_2$ is free to propose its own value `"Val_B"`. None of the three acceptors have seen any proposal > 20, so all three reply with Accepted(20, "Val_B"). Since 3 of 5 is a majority, `"Val_B"` is safely and permanently committed.

Problem 2: Binary Protobuf Decoding
Varint Byte Stream Analysis

The following raw byte stream is received over a network socket: 08 96 01

Question a: Determine the Field Number and Wire Type.
Question b: Decode the integer value.

Step-by-Step Solution:

a) Decoding the Key Byte (0x08):
0x08 = 0000 1000 in binary.
• Wire Type = 3 lowest bits: 0000 1000 & 0x07 = 000 = Wire Type 0 (Varint).
• Field Number = Shift right by 3 bits: 0000 1000 >> 3 = 00001 = Field Number 1.

b) Decoding the Varint Payload (96 01):
• Byte 1 (0x96) = 1001 0110. MSB = 1 (more bytes follow). Data bits: 0010110.
• Byte 2 (0x01) = 0000 0001. MSB = 0 (terminal byte). Data bits: 0000001.
Concatenating in Little-Endian (Byte 2 is higher order bits):
Binary = 0000001 0010110 = 1100 1000 in binary.
Decimal = $128 + 16 + 4 = \mathbf{150}$.

Problem 3: Distributed Consistency
Gifford Quorum Sizing & Fault Tolerance

A distributed database cluster has $N = 7$ replicas. The write quorum size is set to $W = 5$.

Question a: What is the minimum read quorum size $R$ to maintain strong consistency?
Question b: How many concurrent server crashes can the cluster tolerate during writes and reads?

Step-by-Step Solution:

a) Consistency condition: $R + W > N \implies R + 5 > 7 \implies R > 2 \implies \mathbf{R = 3}$.
Split-brain check: $W > N / 2 \implies 5 > 3.5$ (satisfied).

b) Fault tolerance:
• Write operations ($W = 5$): Needs 5 surviving nodes out of 7 $\to$ Tolerates $7 - 5 = \mathbf{2}$ failed servers.
• Read operations ($R = 3$): Needs 3 surviving nodes out of 7 $\to$ Tolerates $7 - 3 = \mathbf{4}$ failed servers.

Problem 4: Cloud Datastore
GAE Entity Groups & Funds Transfer

A developer implements bank accounts on Google App Engine. Each account is an independent root entity. A transfer must deduct \$50 from Account A and add \$50 to Account B.

Question: Can this be executed in a standard GAE transaction? What feature is required and what are its limits?

Step-by-Step Solution:

• Standard Transaction: No. Standard GAE transactions are strictly confined to a single Entity Group (entities sharing an ancestor). Because Account A and B are independent root entities, they reside in separate Entity Groups.
• Required Feature: Cross-Group (XG) Transactions must be enabled (options.setXG(true)).
• Limits: GAE restricts XG transactions to a maximum of 5 Entity Groups.

Problem 5: Browser Sandboxing
NaCl 64-Byte Alignment Analysis

Question: Why does Google Native Client (NaCl) prohibit indirect jumps to unaligned addresses, and how does 64-byte alignment stop attacks?

Step-by-Step Solution:

• The Attack: x86 opcodes have variable byte lengths. A sequence of harmless instructions may contain byte fragments that, if decoded starting from an unaligned offset in the middle of an opcode, form prohibited instructions (e.g. direct syscalls or segment register manipulation).
• The Defense: NaCl mandates that all branch targets align to 64-byte multiples. Compilers pad instructions with NOPs so every 64-byte boundary contains a vetted, valid instruction start. Indirect jumps are forced to mask out the bottom 6 bits (and $0xffffffc0, %reg), making it mathematically impossible to jump into the middle of an instruction.
